# Mermaid tasks

Spec: `doc/diagram-model.md` (section 1), `doc/architecture.md` (3, 4.5, 5.3, 6.3), roadmap lines 13-15 and the "Mermaid" phase table (M1-M3) in `doc/plan.md`. Scope: the Mermaid engine only; dot, D2 and PlantUML are separate issues that reuse `graph/` afterwards.

## Decisions for the plan

- Layering follows `doc/architecture.md` 3 unchanged: `mermaid/` and `graph/` depend on `core/` only; `document/render.lua` calls `mermaid.render(lines, ctx) -> Output` directly (4.5) behind `safe()` (pcall plus Output validation, failure -> `core/errbox`). No new layer, no registry between renderer and engine.
- `core/canvas.lua` and `core/errbox.lua` do not exist yet; they arrive in task 1 because the first slice (one node, error box) needs them.
- Standalone `.mmd`/`.mermaid` (6.3): the session's frontend becomes a per-buffer choice (today `session.lua` hard-wires `markdown.block`). The diagram-file frontend builds a `document.model` with a single `code_block{lang="mermaid"}` spanning the buffer (`document/diagram_file.lua`, which may know `document/model`; `mermaid/` stays unaware), so the one renderer, the one `safe()` path, the cache and the source map are reused. Source map is the single entry the renderer already produces for an atomic block.
- Engines are atomic blocks: one map entry for the whole source range (4.1, 5.4 "positions inside a diagram map to the diagram block start"). Diagram rows carry highlight spans from the shared canvas (border, edge, label groups defined in `core/highlight.lua`).
- Types are registered in `mermaid/registry.lua` (type name -> module with `render(lines, ctx)`); unknown or unimplemented types go to `core/errbox` labelled with the type name, never raise.
- Every layout loop (per layer, per edge-routing pass) calls `core/job.yield_point()` (5.3); it is a no-op outside a job so specs stay synchronous.
- Width rule (diagram-model.md 1): compact spacing, then flowchart direction to top-down, then boxed source with a note. No output line is ever wider than `ctx.width`; the invariant is asserted in unit, golden and integration tests.
- Config: `engines.mermaid = false` renders the block as plain code (task 4). `mermaid = { enabled }` stays as validated today; the coder records in task 4 whether it is merged into `engines.mermaid` or left reserved.
- Flowchart facts (nodes, edges, labels, shape names, subgraph membership, direction) are projected by a `tests/` module and compared in own-input pairs under `tests/pairs/mermaid/` (`doc/testing.md` 3.2). Layout is checked by invariants and goldens, not pixels.
- Tasks 14-23 (M2 class, state, ER; M3 pie, gantt) were expanded from outlines into parser and render slices; each may still be adjusted when it becomes next (`doc/plan.md` principle "plan just in time"). Class, state and ER share the record-node and edge-end kit of task 14 and the width policy extracted in task 16. Task 24 is the final gates, task 25 a recorded fix.
