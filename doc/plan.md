# nvim-doc-preview: project plan

Delivery order and workflow. Design is in `doc/architecture.md`; section
numbers below refer to it.

## Principles

* **Vertical slices.** One feature at a time, full stack: parser, document
  model, renderer, tests (unit, golden, integration where relevant). A
  slice is done when a user could see the feature in a preview buffer.
* **Plan just in time.** Only the next slice is planned in detail. Later
  slices are one-liners in the roadmap and get their detail when they
  become next.
* **Infrastructure arrives with the first slice that needs it** (pair
  runner, source map, async runner, ...), never as a standalone
  horizontal step. The one exception is the test framework (issue 0001).
* **Reference pairs grow per slice.** Each slice adds own inputs for the
  matching spec section (e.g. CommonMark "ATX headings"), with `cmark`
  expectations, into
  `tests/pairs/` and reports pass/skip counts (`doc/testing.md` 2).

## Issues

One file per planned slice in `issue/<name>.md` (no numeric prefix in the
file name; the number is in the file's title line `# NNNN Name`), numbered
in delivery order. Only the next issue is fully detailed; later ones start
as an outline (status `outlined`) and are detailed when they become
next. Template:

```
# NNNN Name
Status:       outlined | planned | in progress | done
Goal:         user-visible outcome, one sentence
Touches:      modules / test layers involved
Tasks:        short checklist (each fits one coder dispatch)
Done when:    observable acceptance, incl. which tests must pass
Out of scope: what is left for later issues
```

## Roadmap (not yet planned in detail)

Order is a proposal; each line is one or a few issues. Promote a
line to `issue/` when it becomes next.

**Walking skeleton, Markdown** (issue numbers in brackets)

1. *Async render pipeline*: issue 0002. **Done.**
2. *Paragraph, real*: issue 0003. **Done.**
3. *Heading* (ATX, then setext) [0004, planned]: first slice with
   reference pairs, so it brings the pair runner, the AST->HTML
   projection, highlight spans, `LICENSE`, `NOTICE`, `doc/references.md`.
   Pairs use our own inputs with expected output generated by `cmark`
   (dev-only oracle); spec text and examples are not copied
   (`doc/testing.md` 2).
4. *Quality gates* [0005]: stylua, luacheck, size, banned APIs, `make ci`.
5. *Inline emphasis/strong/code span* [0006]: `markdown/inline`, plus
   strike, hard breaks, escapes and entities.
6. *Links* [0007]: inline, reference, autolinks, `[n]` list at end.
7. **Done** (host: `make ci` stylua/luacheck). Scroll/cursor sync both ways +
   loop guard, `q`, `:DocPreview sync on|off` [0008].
8. **Done** (host: oracle expectations, pair baseline, `make ci`). One slice each: *thematic break* [0009], *block quote* [0010],
   *lists* [0011], *fenced code (plain) + indented* [0012], *HTML blocks*
   [0013], *tables* [0014], *images (placeholder)* [0015], *footnotes*
   [0016].
9. **Done** (host: see issue statuses). *Resize* re-render [0017],
   *config + validation* [0018], *large-file guard* [0019], *layouts*
   `vsplit|hsplit|replace` [0020].

**Code highlight**

9. *Treesitter highlight* in `core/codeblock`, plain fallback.
10. *`core/errbox`*: error and unsupported-block fallback (needed
    earlier if a slice has to degrade).

**RST** (each slice reuses the shared renderer; first one proves the
second frontend)

11. *RST paragraph + section title* (adornment levels).
12. Then per construct: inline markup, lists, literal blocks, block
    quotes, transitions, tables (simple, grid), field/definition lists,
    admonitions, `code-block`, images, unknown-directive box.

**Diagrams** (slices are per feature, not per whole diagram type)

13. *Mermaid, engine dispatch + one node*: `mermaid/` skeleton, `.mmd`
    standalone file, fenced block in md, errbox on failure.
14. *Flowchart*: edges, labels, directions, shapes, subgraphs, width
    fallbacks (done).
15. *Sequence diagram* (parse, layout, drawing: done), then M2/M3 types, *dot*, *D2*, *PlantUML*: see
    phase tables below; each type is a slice, larger ones are split by
    feature.

**Cross-cutting, scheduled by need**

* Quality gates (`doc/testing.md` 5: stylua, luacheck, size, banned
  APIs, `make ci`): issue 0005, right after the heading slice.
* Incremental block cache (4.4), after async and after perf budget is
  measured.
* `:checkhealth doc_preview` and `:help` docs (done: `lua/doc_preview/health.lua`,
  `doc/doc_preview.txt`), `LICENSE`/`NOTICE`,
  `doc/references.md` entries (the last two are written by whichever
  slice first ports code or copies test data).
* GitHub Actions CI (`.github/workflows`): run `make ci` on a Neovim
  version matrix (minimum 0.10, stable, nightly) on Linux and macOS.
  Written (`.github/workflows/ci.yml`), awaiting first run
  (`issue/ci-workflow.md`).
* Release packaging. Not started:
  * Tagged releases (semver) with a changelog.
  * LuaRocks: a rockspec listing only runtime files (`plugin/`, `lua/`,
    `doc/doc_preview.txt`) and a publish workflow
    (`luarocks-tag-release`).
  * Optional lean release branch with only runtime files, so plugin
    managers that `git clone` skip `tests/`, `tools/` and `issue/`
    (`.gitattributes` `export-ignore` only slims archives).
* Optional: `lua-language-server --check` (type check) as a quality
  gate in `make ci`.

## Diagram type phases

Mermaid (`doc/diagram-model.md` 1):

| Phase | Types |
|---|---|
| M1 | flowchart/graph (nodes, edges, labels, shapes reduced to box variants, subgraphs), sequence diagram |
| M2 | class diagram (done), state diagram (done), ER diagram (done); M2 complete |
| M3 | pie (done), gantt (done); M3 complete, others later |

PlantUML (`doc/diagram-model.md` 2):

| Phase | Types |
|---|---|
| P1 | sequence, class |
| P2 | activity (new syntax), state, use case, component, object |
| P3 | gantt, mindmap, others (anything else stays boxed source) |

## Per-component workflow

Applies when a slice introduces a new component (a parser, an engine),
scoped to what that slice covers: (1) record references and licences in
`doc/references.md` (gate `doc/testing.md` 4.2); (2) extract the official
pairs for this slice's feature and commit them with provenance; (3) run
them first, mostly failing, as the backlog; (4) port what the licence
allows, write the rest, until the pass rate meets the slice target; (5)
review skipped/deviating pairs; (6) add hand-reviewed goldens and
headless integration tests; (7) update `NOTICE` and headers.
